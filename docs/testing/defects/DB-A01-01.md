# DB-A01-01 — Valid customer sensitive upload may be denied by policy subquery RLS

## Current disposition — 2026-10-29

Original static code defect resolved locally; not an unresolved High implementation finding. Live Supabase Storage acceptance remains a separate environment gate, not a claim that this defect persists.

A06 reviewed the current source: migration002's `storage_intent_bound_insert` now calls the target-bound `SECURITY DEFINER` helper `can_insert_storage_object(text,text)` rather than doing the supporting-table join as the authenticated policy invoker. The helper pins `search_path = public, pg_temp`, revokes PUBLIC execute and grants authenticated execute only. It checks exact bucket/key, PENDING_UPLOAD, unconsumed/unexpired intent, purpose and customer/admin authority without broad customer SELECT grants. Migration003 preserves the execute-only normal-principal boundary; migration004 hardens claim validation; migration005 replaces the helper with the same private-purpose constraints plus exact intent-bound public product uploads. No private bucket becomes public.

Runtime SQL evidence is attributed to A01, not an independent A06 rerun: `A01-critical-workflow-completion.md` reports clean migrations001–005/seed plus `tests/rls/access.sql`, `storage.sql`, `storage-intent.sql`, RPC boundary and lifecycle suites on real PostgreSQL17. `storage-intent.sql` asserts valid-customer helper allow and wrong-bucket/key, consumed, expired and cross-customer denies. The main lifecycle repeatedly creates and authorizes exact upload intents without supporting-table customer grants. These scripts and current helper source were independently read by A06. A06 composed HTTP tests additionally prove selected-principal authorization precedes scanner authority and denied ownership does not retry as the other identity.

This resolves the reported invoker-RLS cause at source/local SQL scope. It does not prove live Supabase PostgreSQL15 Storage HTTP signed-PUT/read/expiry, actual JWT signatures, deployed helper ownership or scanner behavior. A07/A05 must retain those staging allow/deny checks and policy review; A00 must not turn local closure into provider acceptance. The original unobserved finding below is retained as history.

## Severity and scope

**High (static finding; runtime not yet observed).** The sensitive Storage insert policy appears unable to see the customer-owned intent/evidence rows that it queries. If confirmed, valid customer KYC and payment-slip uploads are unavailable. This is not an authorization bypass finding. A01 owns `supabase/**`; A06 has not modified the migration.

## Static evidence

In `supabase/migrations/202607130002_rls_and_storage.sql`, policy `storage_intent_bound_insert` on `storage.objects` uses an `EXISTS` subquery joining `public.evidence_objects` and `public.upload_intents` to validate the exact bucket/key, purpose, expiry, consumption state, and actor.

The same migration enables and forces RLS for both tables and revokes broad access. `evidence_objects` has SELECT policies only for Reviewer/Owner KYC/slip reads and Operations/Owner condition reads; an authenticated customer cannot select its own KYC/slip evidence row. `upload_intents` has no authenticated SELECT grant/policy in the reviewed migration. Under invoker policy evaluation, the subquery is therefore expected to see no qualifying row or raise a permission error for a customer, even when the intent is valid.

## Expected vs likely actual

- Expected: Customer with a valid server-minted DB JWT can insert the exact one-object key for its own unexpired, unconsumed KYC/payment intent. Cross-user, expired, consumed, wrong-purpose, wrong-bucket and wrong-key attempts deny.
- Likely actual: Valid customer insert denies because the policy subquery cannot read one or both supporting rows.
- Runtime status: **not run**; no runnable Supabase/PostgreSQL environment is available. This report must not be cited as an observed database failure.
